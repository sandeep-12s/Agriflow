# AgriFlow — Deployment Guide

A step-by-step guide to deploying AgriFlow for real, using free-tier
services. This complements — doesn't replace — the "Running it" section
in the main README, which covers local development only.

## Why PostgreSQL instead of SQLite here

Local development uses SQLite because it needs zero setup. **Production
can't use SQLite** on Render, Railway, or most similar platforms — their
web services have an *ephemeral filesystem*, meaning every redeploy or
restart wipes any file the app wrote, including a SQLite database file.
AgriFlow was built with this in mind from Step 2 onward: `DATABASE_URL`
is read from an environment variable everywhere, and
`app/db/database.py` already branches its SQLite-only setting
(`check_same_thread`) based on the URL scheme — switching to Postgres
needs no code changes, just a different `DATABASE_URL` and one new
dependency (`psycopg2-binary`, already added to `requirements.txt`).

## Recommended stack (all free-tier)

| Piece | Service | Why |
|---|---|---|
| Backend + database | [Render](https://render.com) | Free web service + free PostgreSQL, both provisioned together from `render.yaml` |
| Frontend | [Vercel](https://vercel.com) or [Netlify](https://netlify.com) | Zero-config static hosting for a Vite build, generous free tier |

Free-tier limits and exact plan names change over time on any hosting
platform — check each one's current pricing page before relying on it
for a real launch, not just this guide.

## 1. Backend + database on Render

1. Push this repo to GitHub, if you haven't already.
2. In the Render dashboard: **New → Blueprint**, and point it at your
   GitHub repo. Render reads `render.yaml` from the repo root and
   provisions two things together:
   - A **PostgreSQL database** (`agriflow-db`)
   - A **web service** (`agriflow-backend`) with `DATABASE_URL` already
     wired to that database, and `SECRET_KEY` auto-generated — neither
     ever needs to be typed in by hand.
3. Render will prompt for any env var marked `sync: false` in
   `render.yaml` — that's `ANTHROPIC_API_KEY`. Paste your real key here,
   or leave it blank to run on the fallback-only assistant.
4. Once deployed, note your backend's public URL — something like
   `https://agriflow-backend.onrender.com`.
5. **Seed the production database once** — it starts completely empty.
   From your own machine, temporarily point at the live database:
   ```powershell
   cd backend
   $env:DATABASE_URL = "<paste the External Database URL from Render's Postgres dashboard>"
   python -m app.db.seed
   ```
   (On macOS/Linux: `export DATABASE_URL="..."` instead.) Close that
   terminal afterward so `DATABASE_URL` doesn't linger in your shell and
   accidentally point local development at the production database.
6. Come back and update `CORS_ORIGINS` on the Render service once you
   know your frontend's real URL (step 2 below).

## 2. Frontend on Vercel

1. In Vercel: **New Project**, import the same GitHub repo.
2. Set **Root Directory** to `frontend`.
3. Framework preset: Vite (should auto-detect).
4. Add an environment variable: `VITE_API_URL` = your Render backend URL
   from step 1.4 above (no trailing slash).
5. Deploy. Vercel builds with `npm run build` and serves `dist/` — the
   included `frontend/vercel.json` handles the SPA routing fallback for
   you (without it, refreshing on any page besides `/` would 404, since
   there's no `/produce` file on the server — only client-side React
   Router knows about that route).
6. Copy your new Vercel URL (e.g. `https://agriflow.vercel.app`) and go
   back to Render to update `CORS_ORIGINS` to include it.

### Using Netlify instead

Same idea: **Base directory** `frontend`, build command `npm run build`,
publish directory `frontend/dist`, same `VITE_API_URL` env var.
`frontend/public/_redirects` already handles Netlify's version of the
SPA fallback — no extra config needed there.

## 3. Environment variables — production checklist

**Backend (Render):**

| Variable | Source |
|---|---|
| `DATABASE_URL` | Auto-wired by `render.yaml` from the Postgres database |
| `SECRET_KEY` | Auto-generated by `render.yaml` — never reuse the local dev value |
| `CORS_ORIGINS` | Your real frontend URL(s), comma-separated |
| `ANTHROPIC_API_KEY` | Optional — entered in Render's dashboard when prompted, never committed to a file |
| `ASSISTANT_MODEL` | `claude-haiku-4-5-20251001` (or your own choice) |

**Frontend (Vercel/Netlify):**

| Variable | Value |
|---|---|
| `VITE_API_URL` | Your deployed backend's URL |

## 4. Final testing checklist (against the live URLs, not localhost)

Same shape as the manual QA checklist in `SECURITY.md`, but pointed at
production this time:

- [ ] Register a new account on the live frontend
- [ ] Log in, reach the dashboard
- [ ] Add a produce entry, confirm it appears in the list
- [ ] Get a recommendation for it — confirm real numbers, not an error
- [ ] Check Market, Buyers, Storage, and Processing pages all load seeded data
- [ ] Ask the Assistant a question — confirm it replies (fallback or AI)
- [ ] Refresh the browser while on a non-home route (e.g. `/produce`) —
      confirm it does **not** 404 (this is exactly what the SPA rewrite
      config exists to prevent)
- [ ] Open DevTools → Network tab, confirm no request goes to
      `localhost` — everything should hit your real Render URL

If any step fails, the most common cause is a mismatched
`CORS_ORIGINS` (backend) vs `VITE_API_URL` (frontend) — once live, both
need to point at each other's *real* deployed URLs, not `localhost`.
